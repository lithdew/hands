# Ishaan / Hands — an engineered personal site

The site should feel like the public notebook of someone making a new way to use a computer: precise, curious, and confident. It needs a memorable visual idea and one interaction worth trying. A technically valid collection of headings and rectangular cards is not an acceptable result.

## Direction

Use warm off-white paper, near-black ink, and a decisive cobalt blue. Keep the palette disciplined. Large editorial type, fine rules, small monospaced annotations, offset alignments, and deliberate changes in scale should establish the identity. Use local/system font stacks skillfully; no dependency on remote fonts. Broad whitespace needs a compositional purpose, not an empty hero followed by three cards.

Choose an asymmetric grid and a strong typographic opening around Ishaan Batra and the work on Hands. The first desktop viewport should already communicate the project and contain a distinctive piece of product illustration. At 390px, redesign the composition into a confident vertical sequence rather than simply shrinking the desktop layout. Put useful content near the top. Avoid giant mobile gaps, truncated headings, and microscopic diagram labels.

The visual signature is an original Hands workbench: a graphic, inspectable explanation of how an instruction becomes a specialist handoff and returns to a fast decision. Build it from original HTML/CSS/SVG and JavaScript. Give it the care of a small instrument: clear active state, precise connectors, a meaningful input, an obvious next step, and considered transitions. It should read as a designed interface, not a generic flowchart, a static wireframe, or an unrelated decorative animation.

## Interaction to design

Make the workbench a genuinely functioning local interface study. A visitor can select a task example, step through or replay its instruction → specialist → review → return sequence, and see the active stage and concrete output preview change coherently. A pause/reset or direct stage selection must work. Keyboard interaction and reduced-motion behavior must preserve the same meaning. Show a compact visible “Interactive concept” label so no one mistakes it for a live model or computer connection.

This is not permission to fake a model invocation or fabricate live telemetry. Do not call Hands control endpoints, capture a browser, send messages, or invent loading/success states for a nonexistent service. The interaction itself must be real local state, with honest labels. Do not present a disabled text input, dead slider, pretend video play button, or decorative button as a working feature.

Use measured microinteractions elsewhere: underline movement, row focus, a changing diagram, and a restrained arrival animation. Animations should have a reason. Avoid cursor followers, magnetic buttons, background particles, relentless marquee text, and large scroll reveals that hide content or make screenshots blank. Respect prefers-reduced-motion, and keep the page usable before JavaScript runs.

## Content and structure

Create a personal homepage and a distinct Hands work/project page. Choose their final layout; do not reuse the old site's arrangement. The pages must link clearly in both directions. Use concise, specific copy. Known facts are enough: Ishaan Batra is building Hands and working on the transition between computer-use decisions and general-agent reasoning, speed, correctness, and user corrections.

Show two or three particular experiments from the supplied evidence, not vague “AI solutions.” A calculus study pack, a reinforcement-learning reading brief, and a matrix-inversion lesson are available. Make their presentation feel editorial: varied scale, short meaningful descriptions, and original lightweight visual excerpts or diagrams. Do not make a row of three identical service cards or an invented portfolio of clients. If an output preview is illustrative rather than a source screenshot, label it naturally as an illustration. Do not claim the previous outputs establish visual excellence, commercial traction, or general reliability.

Keep provenance in README/provenance.json and an unobtrusive short about note. Public visitors should learn what Ishaan is making, what the interface lets them try, and what the experiments produced. They should not have to read source-packet mechanics, evaluator terminology, repeated disclaimers, internal UUIDs, or a compliance checklist. One calm “In development” note is enough for project status. No invented employer, degree, location, portrait, contact details, testimonials, funding, clients, social profile, or founder biography.

## Acceptance standard

The result needs a recognizable graphic idea, strong type and spacing, coherent composition, readable hierarchy, and at least one rewarding interaction. Desktop and mobile should both look intentionally designed. A screenshot should show a finished personal/work site, not a generated template, a text document wearing a website shell, or a dark dashboard full of generic panels.

Check the workbench's real state changes, keyboard behavior, reduced motion, back/home links, and all visible buttons. Check all four initial desktop/mobile page views, then inspect the actual workbench and one lower-page content region. No navigation dead ends, fake contact action, errors, clipped text, or unreadable labels. Critique visual craft explicitly, even if all overflow checks pass.

Produce complete local HTML/CSS/JS files through Hands. The evaluation coordinator supplies this brief and independent feedback, never the final site code. Use Astra low for the design and synthesis in this run. Keep the code compact and purposeful; no build tool, dependency installation, external asset service, analytics, or unexecuted React project is needed.
